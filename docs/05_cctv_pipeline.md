# 5. 6차 — 저화질 CCTV 다중 클래스 탐지 파일럿

> bear 프로젝트(1~5차)와는 연구 질문이 다르다. bear는 "COCO에 절대적으로
> 부족한 희소 클래스를 생성모델로 보완"하는 문제였고, 이번은 "이미 흔한
> 클래스(사람·차량·소지품)를 화질이 나쁜 CCTV에서도 놓치지 않게 만들기"다.
> 클래스가 희소하지 않으므로 생성모델로 데이터를 늘릴 필요는 없다 — 1~5차에서
> 검증된 **강건화 학습(clean+열화 병행)**과 **복원 전처리(NAFNet+Real-ESRGAN)**
> 를 다른 도메인에 그대로 적용해 결과가 재현되는지 확인하는 것이 이 파일럿의
> 목적이다.

## 5.0 범위 확정 — "찾기"의 의미

최초 요청은 "저화질 CCTV에서 수배자 혹은 실종자 찾기"였다. 이는 두 가지로
해석될 수 있다 — ① 사람·소지품 등을 일반 객체로 탐지, ② 특정 개인의 얼굴을
매칭해 신원을 특정(얼굴인식/재식별). 사용자에게 확인해 **①(일반 객체 탐지)**
로 범위를 확정했다 — 특정 개인을 식별하는 기능은 만들지 않는다.

## 5.1 클래스 선정 — 8개

| COCO 원본 category_id | ultralytics 인덱스 | 이름 |
|---|---|---|
| 1 | 0 | person |
| 2 | 1 | bicycle |
| 3 | 2 | car |
| 4 | 3 | motorcycle |
| 6 | 5 | bus |
| 27 | 24 | backpack |
| 31 | 26 | handbag |
| 33 | 28 | suitcase |

"사람 + 동행 소지품/이동수단"이라는 CCTV 수색 시나리오에 맞춘 조합이다.
OD-VIRAT(person/car/vehicle/carrying_object/bike, 실제 CCTV 전용 벤치마크,
https://github.com/hayatkhan8660-maker/OD-VIRAT)이 거의 동일한 클래스 구성을
가진 더 적합한 후보였으나 **Google Drive 폴더 배포라 스크립트로 재현 가능한
다운로드가 어려워 이번 파일럿에서는 보류**했다. 대신 이미 검증된 COCO 파이프
라인(1차부터 써 온 다운로드·분석 도구)을 그대로 재사용했다 — 8개 클래스 모두
COCO에 흔해서 데이터 확보 자체는 문제가 아니었다.

## 5.2 데이터 구성

구현: [scripts/20_build_cctv_dataset.py](../scripts/20_build_cctv_dataset.py)

COCO train2017에서 8개 클래스 중 하나 이상이 있는 이미지를 모으되, **여러
클래스가 동시에 등장하는 사진(사람+가방, 사람+자전거 등)을 우선** 선택해
CCTV 장면에 더 가깝게 만들었다. 총 680장을 세 용도로 나눴다.

| 용도 | 장수 | 비고 |
|---|---|---|
| 학습(clean) | 420 | Albumentations 열화본과 쌍으로 학습에 사용 |
| 학습(deg) | 420 | 위와 동일 이미지에 MotionBlur+Downscale 적용, bbox는 리사이즈 왕복이라 좌표 불변 |
| 검증(val, 학습분포 내) | 40쌍(80장) | 학습 중 모니터링용 |
| 홀드아웃 풀 | 220 | **학습에 전혀 안 씀** — real_lowq_cctv 선정 전용 |

## 5.3 실제로 겪은 두 가지 버그

**① COCO raw category_id vs ultralytics 연속 인덱스 혼동.** 라벨을 쓸 때
`a["category_id"]`(COCO 원본 JSON 값: person=1, bicycle=2, car=3, motorcycle=4,
bus=6, backpack=27, handbag=31, suitcase=33)를 ultralytics의 연속 0-79
인덱스로 착각해 그대로 썼다. 처음 학습·평가를 돌렸을 때 **baseline이 clean
이미지(cctv_val)에서조차 mAP@0.5 0.003**이 나와서 발견했다 — 사전학습된
YOLO26이 사람·차를 못 찾을 리 없으니 검출기가 아니라 라벨이 잘못됐다고
바로 알 수 있었다. `category_id → 이름 → ultralytics 인덱스`를 명시적으로
거치는 `catid_to_yolo` 매핑을 만들어 고쳤다. 고친 뒤 baseline이 cctv_val
0.352, real_lowq_cctv 0.513으로 정상 범위에 들어왔다.

**② restore.py 리팩터링 중 메서드 자체가 사라짐.** 5차에서 `Restorer.restore()`
의 docstring을 고치다가 `@torch.no_grad()` 데코레이터와 `def restore(...)`
선언 줄을 실수로 함께 지워버렸다 — 그 결과 docstring과 본문이 `__init__`
안으로 흘러들어가 `restore()` 메서드 자체가 없어졌다. CCTV 복원을 처음
실행했을 때 `NameError: name 'bgr' is not defined`로 발견했다. **이 버그는
5차 커밋에도 이미 포함돼 있었다** — bear 프로젝트의 5차 결과 자체는 버그가
생기기 전에 이미 만들어져 있어 결과값은 무사하지만, 그 시점 이후로 저장소를
그대로 재현하려 하면 깨졌을 것이다. 즉시 메서드 구조를 복구했다.

두 버그 모두 "평가 결과가 상식적으로 말이 안 되면 코드부터 의심한다"는
원칙으로 잡았다 — baseline이 쉬운 조건(clean, 흔한 클래스)에서 이상하게
낮으면 거의 항상 라벨/파이프라인 버그다.

## 5.4 결과

학습: YOLO26n, 백본 앞 10개 층 동결, AdamW lr0=0.001, 40 epoch, cctv_synth
(840장, clean+deg). bear와 달리 이 8개 클래스는 이미 COCO 최빈 클래스라
재앙적 망각을 볼 별도의 정칙화 표본(reg_fit)을 넣지 않았다.

| 세트 | 지표 | baseline | finetuned | Δ |
|---|---|---|---|---|
| **real_lowq_cctv** (진짜 저화질) | mAP@0.5 | **0.513** | 0.423 | -0.090 |
| real_lowq_cctv | recall | 0.450 | 0.405 | -0.045 |
| real_lowq_cctv + 복원전처리 | mAP@0.5 | 0.054 | 0.046 | -0.008 |
| cctv_val (clean, 학습분포 내) | mAP@0.5 | 0.352 | 0.340 | -0.012 |

![CCTV 결과](figures/fig15_cctv_results.png)

### 해석

**파인튜닝이 여기서도 도움이 되지 않았다** — 심지어 **학습 분포 내부
(cctv_val)에서도 근소하게 나빠졌다**(-0.012). bear 때와 원인이 다르다고
본다. bear는 사전학습 모델이 그 클래스를 거의 몰랐던 반면(37개 small
인스턴스), 이 8개 클래스는 COCO에서 가장 흔한 축에 속해 사전학습 가중치가
이미 강하다. 840장짜리 소규모 파인튜닝 배치로는 이미 강한 표현을 더
개선하기보다 흔들어 놓을 가능성이 높다 — **"이미 잘하는 것을 적은 데이터로
더 잘하게 만들기"는 "거의 못하던 것을 데이터로 채우기"(bear)보다 훨씬
어려운 문제**라는, 이 프로젝트 전체를 관통하는 결론을 다시 한번 확인했다.

**복원 전처리는 이번에도, 오히려 더 심하게 실패했다** — baseline 기준
0.513 → 0.054로 폭락(-0.459, bear의 -0.671 상대 하락률과 비슷한 규모).
샘플 4장을 육안으로 확인한 결과 **전부 예외 없이 격자 아티팩트로 완전히
망가졌다**(bear는 일부만 그랬다). 비 오는 거리, 숲 속 자전거, 오토바이,
야간 거리 — 도메인·조명·질감이 전부 다른데도 실패 양상이 동일했다. 이는
5차에서 잠정적으로 내린 결론("Real-ESRGAN이 스무스한 이미지에서만 실패")을
넘어서는 증거다 — **적어도 이 체크포인트(RealESRGAN_x4plus) + 이 전처리
순서(NAFNet 디블러 후 4배 업스케일 후 축소) 조합은 도메인을 가리지 않고
실제 저화질 사진 전반에 위험하다**고 보는 게 더 정확하다.

## 5.5 bear 프로젝트와의 비교

| | bear (1~5차) | CCTV 파일럿 (6차) |
|---|---|---|
| 문제 유형 | 절대적 희소 클래스 (37개 small 인스턴스) | 흔한 클래스, 화질 저하만이 문제 |
| 생성모델 필요성 | 필수 (데이터 자체가 없음) | 불필요 (COCO에 이미 풍부) |
| 파인튜닝 효과(진짜 저화질) | 개선처럼 보였으나(+0.079) 자체열화 과적합으로 판명 | 처음부터 악화(-0.090), 학습분포 내부도 악화 |
| 복원 전처리 효과 | 악화(-0.671, 일부 이미지만 격자 아티팩트) | 악화(-0.459, 전 샘플 격자 아티팩트) |
| 공통 결론 | 진짜 저화질로 검증해야 착시를 피한다; 현재 복원 모델 조합은 득보다 실이 크다 | 동일 |

두 프로젝트가 서로 다른 데이터·클래스·도메인에서 **같은 두 가지 결론에
독립적으로 도달**했다는 것 자체가 이 결론들의 신뢰도를 높인다.
